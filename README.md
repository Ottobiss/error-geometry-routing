# error-geometry-routing

Эксперимент с маршрутизацией между малой (SegFormer-B0) и большой (SegFormer-B2) моделями семантической сегментации по предсказанной неопределённости. Неопределённость гиперболическая, по HyperUL (Chen, Peng, Cao, Röning, «Hyperbolic Uncertainty Aware Semantic Segmentation», IEEE T-ITS 2023). Малая модель предсказывает свою неопределённость и неопределённость большой модели. Если на кадре малая модель заметно менее уверена, чем, по прогнозу, будет большая, весь кадр обрабатывает большая. Модели обучаются на Cityscapes и тестируются на ACDC; инференса на новых изображениях в проекте нет.

## Как устроен пайплайн

Обе модели — SegFormer, уже обученные на Cityscapes (веса NVIDIA с Hugging Face). Сеть заморожена, обучается только её последний 1×1 conv — слой, на который действует HyperUL. Как в статье, его выход, по каналу на класс, — это евклидов эмбеддинг. Он отображается в шар Пуанкаре: координаты точки служат логитами классов, а расстояние до центра даёт неопределённость (Eq. 15). Обученный классификатор NVIDIA сохраняется вместе с весами, а его выход перед отображением умножается на `model.classifier_scale`: предсказания остаются теми же, а множитель задаёт, где стартуют эмбеддинги. Неопределённость усредняется по патчам 32×32.

1. **Стадия 1, большая модель B2.** Обучение с лоссом HyperUL: кросс-энтропия, взвешенная гиперболической неопределённостью. Результат в `runs/large`.
2. **Стадия 2, экспорт.** Обученная B2 один раз считает неопределённость каждого патча каждого кадра val. Этих кадров не видели ни она, ни исходная сеть NVIDIA. Карты сохраняются в PNG и дальше не меняются. Результат в `runs/large/uncertainty/val`.
3. **Стадия 3, малая модель B0.** Сегментация (HyperUL по собственной неопределённости) учится на кадрах train. Отдельный выходной канал — предсказание неопределённости B2 — учится через BCE на кадрах val по картам из стадии 2. Логиты классов на val не обучаются, поэтому mIoU на val по-прежнему честно отбирает чекпойнт. Результат в `runs/small`.
4. **Выбор порога на val Cityscapes.** Бенчмарк (`src.benchmark`) прогоняет модели на кадрах val. Для каждого кадра считается оценка — разность «своя неопределённость B0 минус её прогноз неопределённости B2», усреднённая по 10% самых неуверенных патчей. Если оценка выше порога, весь кадр обрабатывает B2. Для каждого порога из списка выводятся mIoU и доля кадров с запуском B2. Результат в `runs/benchmark_val`.
5. **Тест на ACDC.** Тот же бенчмарк на всех размеченных кадрах ACDC: train и val, 2006 штук (разметка test закрыта). Всё считается по всем кадрам и отдельно по условиям: туман, ночь, дождь, снег. ACDC модели не видели. Кроме маршрутизации, сравниваются B0 и B2 без дообучения и после него, их IoU по классам, калибровка неопределённости, точность прогноза неопределённости B2, решения по патчам, ошибки B0 и статистические тесты (см. «Бенчмарк»). Результат в `runs/benchmark`.
6. **Отчёт.** `src.report` собирает метрики и логи всех стадий в один файл `runs/report/report.md`: формулы, таблицы, графики, примеры кадров (см. «Отчёт»).

Порог маршрутизации выбирают на val Cityscapes. Предсказание неопределённости B2 училось на этих же кадрах, поэтому маршрутизация там выглядит немного лучше, чем на новых данных. Честная оценка — тест на ACDC.

## Требования

- **ОС и GPU.** Linux и NVIDIA GPU с памятью от 10 ГБ, RTX 3080 достаточно. Для `train.amp=true` (bf16) нужна архитектура Ampere или новее: RTX 30xx/40xx, A100 и т. п. На T4 и V100 bf16 нет, там оставьте `train.amp=false`.
- **CPU.** Желательно 8 ядер и больше. При замороженной сети скорость обычно упирается в загрузку данных: декодирование PNG 2048×1024.
- **Память и диск.** RAM 16–32 ГБ, ~12 ГБ диска под Cityscapes. Результаты занимают меньше 1 ГБ.

## Данные

### Cityscapes

С [cityscapes-dataset.com](https://www.cityscapes-dataset.com) (нужна регистрация) понадобятся `leftImg8bit_trainvaltest.zip` и `gtFine_trainvaltest.zip`. После распаковки структура такая:

```
/data/cityscapes/
├── leftImg8bit/{train,val}/<город>/*_leftImg8bit.png
└── gtFine/{train,val}/<город>/*_gtFine_labelIds.png
```

Используются файлы `*_labelIds.png`. Перевод в 19 классов делается на лету, остальные метки игнорируются. Часть test не нужна.

### ACDC

Загрузчик понимает только раскладку Cityscapes. ACDC (папки `rgb_anon/` и `gt/` с [acdc.vision.ee.ethz.ch](https://acdc.vision.ee.ethz.ch)) переводится в неё симлинками, без копирования:

```bash
ACDC=/data/acdc                  # абсолютный путь к папке с rgb_anon/ и gt/
DST=/data/acdc_cityscapes
for split in train val; do
  for cond in fog night rain snow; do
    mkdir -p "$DST/leftImg8bit/$split/$cond" "$DST/gtFine/$split/$cond"
    for img in "$ACDC/rgb_anon/$cond/$split"/*/*_rgb_anon.png; do
      seq=$(basename "$(dirname "$img")"); name=$(basename "$img" _rgb_anon.png)
      ln -sf "$img" "$DST/leftImg8bit/$split/$cond/${name}_leftImg8bit.png"
      ln -sf "$ACDC/gt/$cond/$split/$seq/${name}_gt_labelIds.png" "$DST/gtFine/$split/$cond/${name}_gtFine_labelIds.png"
    done
  done
done
```

ACDC используется только для теста моделей, обученных на Cityscapes:

```bash
python -m src.benchmark configs/benchmark.yaml root=/data/acdc_cityscapes
```

Так оцениваются все размеченные кадры ACDC (train и val, 2006 штук), а условия, лежащие в папках-«городах», дают отдельные группы. Замороженные сети обучены на Cityscapes, поэтому качество на ночи и тумане будет ограничено ими — это и проверяет тест.

## Веса

По умолчанию берутся `nvidia/segformer-b0-finetuned-cityscapes-1024-1024` (малая модель) и `nvidia/segformer-b2-finetuned-cityscapes-1024-1024` (большая). При первом запуске они скачиваются в `~/.cache/huggingface`. Их классификатор на 19 классов сохраняется, его выход умножается на `model.classifier_scale`; у B0 к нему добавляется выход для неопределённости B2. Если на машине нет интернета, скачайте веса заранее и передавайте путь:

```bash
python -c "
from transformers import SegformerForSemanticSegmentation as S
for v in ('b0', 'b2'):
    S.from_pretrained(f'nvidia/segformer-{v}-finetuned-cityscapes-1024-1024').save_pretrained(f'weights/segformer-{v}')
"
# стадия 1: model.pretrained=weights/segformer-b2; стадия 3: model.pretrained=weights/segformer-b0
```

## Запуск

### Пробный запуск

Перед долгим обучением стоит проверить память и скорость:

```bash
python -m src.train configs/train.yaml configs/large.yaml data.root=/data/cityscapes out=runs/try \
  train.iters=200 log.every=20 log.val_every=200
```

В TensorBoard смотрите `train/mem_gb` и `train/img_per_s`. Полное время обучения примерно равно `train.iters × data.batch_size / img_per_s` плюс валидации.

### Одна GPU

```bash
python -m src.train configs/train.yaml configs/large.yaml data.root=/data/cityscapes   # 1. B2 -> runs/large
python -m src.export_uncertainty configs/export_uncertainty.yaml root=/data/cityscapes  # 2. -> runs/large/uncertainty/val
python -m src.train configs/train.yaml configs/small.yaml data.root=/data/cityscapes   # 3. B0 -> runs/small
python -m src.benchmark configs/benchmark.yaml root=/data/cityscapes split=val out=runs/benchmark_val  # 4. порог
python -m src.benchmark configs/benchmark.yaml root=/data/acdc_cityscapes              # 5. тест -> runs/benchmark
python -m src.report configs/report.yaml                                               # 6. -> runs/report/report.md
```

Стадия 2 берёт `runs/large/best.pt`, стадия 3 — кадры train и кадры val с картами из `runs/large/uncertainty/val`, стадии 4 и 5 — оба `best.pt`, отчёт — результаты всех стадий. Эти пути задаются в конфигах (см. «Настройки»). Конкретную карту выбирают так: `CUDA_VISIBLE_DEVICES=1 python -m ...`.

### Две GPU

Обучение (стадии 1 и 3) запускается через `torchrun`, по одному процессу на GPU (DDP):

```bash
torchrun --standalone --nproc_per_node=2 -m src.train configs/train.yaml configs/large.yaml data.root=/data/cityscapes
torchrun --standalone --nproc_per_node=2 -m src.train configs/train.yaml configs/small.yaml data.root=/data/cityscapes
```

- `data.batch_size` и `data.workers` задаются на все GPU сразу и делятся поровну, поэтому батч должен делиться на число GPU. Гиперпараметры получаются те же, что на одной GPU.
- Обучается всего 5–15 тыс. параметров, так что синхронизация между картами почти ничего не стоит.
- Валидирует, пишет в TensorBoard и сохраняет чекпойнты только первый процесс, остальные его ждут. Статистики `train/*` считаются по его части батча, а `train/img_per_s` показывает общую скорость.
- Экспорт и бенчмарк работают на одной GPU и укладываются в 10 ГБ.
- Если `torchrun` зависает на старте (бывает на потребительских картах без NVLink), запускайте с переменной окружения: `NCCL_P2P_DISABLE=1 torchrun ...`.

### Продолжение обучения

```bash
python -m src.train configs/train.yaml configs/large.yaml data.root=/data/cityscapes --resume runs/large/last.pt
```

Чекпойнты пишутся при каждой валидации: `last.pt` — последний, `best.pt` — лучший по `val/mIoU`. `--resume` восстанавливает модель, оптимизатор, расписание lr и номер итерации. Конфиг при этом должен быть тем же: `train.iters` задаёт ещё и длину расписания lr. Работает и под `torchrun`.

### Бенчмарк

```bash
python -m src.benchmark configs/benchmark.yaml root=/data/cityscapes split=val out=runs/benchmark_val  # 4. выбор порога
python -m src.benchmark configs/benchmark.yaml root=/data/acdc_cityscapes                              # 5. тест на ACDC
```

Всё считается по всем кадрам и отдельно по каждой папке-«городу»: условию ACDC или городу Cityscapes. Результаты печатаются в консоль и пишутся в `benchmark.json` и TensorBoard в папке `out`.

**Четыре модели.** B0 и B2 без дообучения и после него.
- **Модели «без дообучения»** строятся по конфигам чекпойнтов из исходных весов NVIDIA, и их предсказания совпадают с исходными.
- **mIoU** даётся с 95% бутстреп-интервалом по кадрам, рядом попиксельная точность и таблица IoU по каждому классу.
- **Парные разности** — дообучение B0, дообучение B2, B2 против B0 — даются с интервалом и двумя p-значениями: по бутстрепу и по критерию Уилкоксона на попиксельной точности кадров.

**Неопределённость дообученных B0 и B2.** Считается так же, как при валидации во время обучения.
- **ECE** гиперболической неопределённости — метрика калибровки из статьи: ECE для 1 − неопределённость по 15 корзинам.
- **Средняя неопределённость на верных и ошибочных пикселях.** На ошибочных она должна быть заметно больше.
- **MAE прогноза.** Средняя ошибка, с которой B0 предсказывает неопределённость B2, по размеченным пикселям.

**Маршрутизация по порогу.** Оценка кадра — разность «своя неопределённость B0 минус её прогноз неопределённости B2», усреднённая по доле `top` (10%) самых неуверенных патчей. Так большой уверенный фон (дорога, небо) не заглушает небольшие неуверенные участки. Если оценка выше порога, весь кадр вместо дообученной B0 обрабатывает дообученная B2. Для каждого порога из `thresholds` выводятся:
- mIoU и доля кадров с запуском B2;
- стоимость в единицах B0: `1 + cost_ratio × доля запусков`;
- доля закрытого разрыва: (routed − B0) / (B2 − B0);
- точность исправлений: какая доля размеченных пикселей отданных кадров исправлена (B0 ошибалась, B2 права);
- полнота исправлений: какая доля всех таких пикселей попала в отданные кадры.

Пороги абсолютные, поэтому порог, выбранный на val Cityscapes, переносится на ACDC без подгонки: результат на ACDC смотрят в строке с тем же порогом.

**Адаптивный инференс по долям кадров.** Та же замена целых кадров, но для каждой доли кадров (`budgets`) B2 получают кадры с наибольшей оценкой. Так сигналы сравниваются при одинаковой доле запусков.
- **Сигналы** дообученной B0, оценка кадра — то же среднее по 10% патчей:
  - `own` — её собственная неопределённость;
  - `gain` — разность «своя минус предсказанная неопределённость B2», как в маршрутизации;
  - `entropy` — энтропия её softmax, базовая линия без гиперболической неопределённости.
- **Ориентиры** — случайный выбор кадров и оракул. Оракул отдаёт кадры, где B2 права на большем числе пикселей; это не обязательно оптимум по mIoU.
- **Производные метрики:**
  - стоимость и доля закрытого разрыва, как выше;
  - эффективность относительно оракула: (adaptive − random) / (oracle − random);
  - AUROC оценки кадра для события «B2 лучше на этом кадре».

**Решения по патчам.** Патч требует B2, если B2 права на большем числе его размеченных пикселей, чем B0.
- **Для каждой доли самых неуверенных патчей** считаются:
  - точность: в какой доле отмеченных патчей B2 действительно нужна;
  - полнота, F1, accuracy;
  - доля патчей, где B2 нужна, как ориентир.
- **Без порога** — AUROC и AP. Сигналы те же: `own`, `gain` и `entropy`.

**Ошибки B0 по патчам.** Насколько сигнал находит ошибки дообученной B0. Доля ошибок патча — неверные размеченные пиксели, делённые на все размеченные; пиксели с меткой 255 не считаются.
- **Полнота по ошибкам** для каждой доли самых неуверенных патчей — какая доля всех неверных пикселей B0 попала в отмеченные патчи. Ошибки считаются в пикселях: патч с 200 неверными пикселями весит в 200 раз больше патча с одним. Это ответ на вопрос маршрутизации: если можно переобработать x% площади, какую часть ошибок B0 это покроет. Главная точка — 10%.
- **AUROC и AP** для двух меток патча: `y50` — неверна хотя бы половина пикселей, `y_any` — хотя бы 10%. Здесь каждый патч считается один раз. AP случайного сигнала равна доле положительных патчей, она тоже выводится.
- **AUROC для `y50` внутри децилей энтропии.** Патчи делятся на 10 корзин по средней энтропии (границы по всем патчам), AUROC считается в каждой корзине и усредняется с равными весами. Внутри корзины энтропия почти одинакова, поэтому метрика показывает, находит ли сигнал ошибки, которые энтропия не различает.

Доли кадров и патчей отсчитываются сразу на всём наборе, поэтому доля запусков по условиям разная. Она тоже выводится.

Для первых `images` кадров каждой папки сохраняются панели, в TensorBoard и в `panels/*.jpg`: кадр, разметка, предсказания B0 и B2, неопределённость B0, её прогноз неопределённости B2, настоящая неопределённость B2 и разность «своя минус прогноз».

### Логи и отчёт

Каждая стадия сама сохраняет свой вывод в лог рядом с результатами: `train.log`, `export.log`, `benchmark.log`. В лог попадают команда запуска со временем, весь вывод скрипта (итоги валидаций, таблицы бенчмарка), предупреждения и трассировка ошибки, если скрипт упал. Прогресс-бары остаются только в консоли. Повторный запуск дописывает лог.

Метрики тоже сохраняются в файлы:
- `metrics.jsonl` — каждая валидация;
- `train.jsonl` — лосс, lr, скорость и память каждые `log.every` итераций;
- `summary.json` — распределение экспортированной неопределённости B2;
- `benchmark.json` — все метрики бенчмарка.

Новый запуск обучения без `--resume` начинает `metrics.jsonl` и `train.jsonl` заново, как и чекпойнты.

После всех стадий отчёт собирается командой:

```bash
python -m src.report configs/report.yaml
```

В `runs/report/` появляются:
- `report.md` — сам отчёт:
  - схема эксперимента и формулы в LaTeX: гиперболическое вложение, неопределённость, HyperUL, маршрутизация и определения всех метрик;
  - настройки стадий, кривые обучения и метрики валидации, экспорт;
  - выбор порога на val Cityscapes: порог с лучшей mIoU маршрутизации среди тех, где B2 получает не больше `max_launch_rate` кадров;
  - все метрики теста на ACDC по условиям, с этим порогом;
  - перебор, если он был;
  - таблица запусков стадий: время, продолжения с `--resume`, число предупреждений и сами предупреждения, ошибка, если запуск упал, и ссылка на полный лог. Остальное из логов — итоги валидаций и таблицы бенчмарка — уже есть в разделах выше;
- `figures/` — графики: обучение, распределение экспорта, маршрутизация, диаграммы надёжности, адаптивный инференс, полнота по ошибкам;
- `panels/` — примеры кадров ACDC;
- `logs/` — копии логов;
- `metrics.json` — все метрики всех стадий в одном файле.

Отчёт можно собрать в любой момент: разделы стадий, которых ещё нет, отмечаются как отсутствующие. Папка самодостаточна, её можно скопировать целиком. `report.md` с формулами открывается в превью VS Code (`Ctrl+Shift+V`) и на GitHub. PDF, если установлены pandoc и xelatex:

```bash
cd runs/report && pandoc report.md -o report.pdf --pdf-engine=xelatex -V mainfont="DejaVu Serif" \
```

## Настройки

### Как передавать

Первый аргумент — базовый YAML. Дальше по порядку можно передать:
- другие YAML, которые перекрывают часть ключей (так устроены `large.yaml` и `small.yaml`);
- пары `ключ=значение` через точку.

Списки берите в кавычки: `'data.crop=[512,1024]'`. Неизвестный ключ вызывает ошибку, это защита от опечаток. `???` в конфиге означает обязательное значение. Итоговый конфиг сохраняется в `<out>/config.yaml` и внутрь чекпойнтов. Экспорт и бенчмарк строят модель по нему, архитектуру отдельно указывать не нужно.

### Обучение: `configs/train.yaml`

`configs/large.yaml` (стадия 1) меняет `out: runs/large`, `model.variant: b2` и `model.pretrained` на веса B2. `configs/small.yaml` (стадия 3) меняет `out: runs/small` и задаёт `data.large_uncertainty: runs/large/uncertainty`.

|---|---|---|
| `seed` | `0` | сид; при нескольких GPU у процесса `seed + rank` |
| `out` | обязательный | папка запуска; её задают `large.yaml` и `small.yaml` |
| `data.root` | обязательный | корень Cityscapes |
| `data.crop` | `[512, 1024]` | кроп при обучении, H × W |
| `data.base_size` | `[2048, 1024]` | базовый размер W × H для случайного масштабирования |
| `data.scale_range` | `[0.5, 2.0]` | диапазон случайного масштаба |
| `data.batch_size` | `8` | общий батч на все GPU |
| `data.workers` | `8` | общее число процессов загрузки данных на все GPU |
| `data.large_uncertainty` | `null` | папка стадии 2; включает выход неопределённости B2 (стадия 3) |
| `data.large_uncertainty_split` | `val` | split, для которого экспортированы карты: его кадры учат только предсказание неопределённости B2, а сегментация учится на train |
| `model.variant` | `b0` | энкодер: `b0` или `b2` |
| `model.pretrained` | `nvidia/segformer-b0-finetuned-cityscapes-1024-1024` | веса: id на Hugging Face или локальная папка; обучается только их последний 1×1 conv декодера |
| `model.manifold` | `poincare` | модель гиперболического пространства, её координаты служат логитами: `poincare` (шар, как в статье, логиты ограничены 1/√c) или `lorentz` (гиперболоид, пространственные координаты растут как sinh расстояния) |

| `model.patch` | `32` | сторона патча в пикселях для усреднения неопределённости; `1` — попиксельно, как в статье |
| `loss.t` | `1.869` | вес пикселя 1 / ln(t + d), Eq. 11 |
| `loss.hr` | `1.0` | OHUEM: доля самых неуверенных размеченных пикселей каждого изображения, по которым считается лосс; `1.0` — все |
| `loss.class_weights` | `null` | список весов 19 классов, Eq. 12 |
| `loss.large_unc_weight` | `1.0` | вес лосса неопределённости B2 (стадия 3) |
| `loss.large_unc_loss` | `bce` | лосс неопределённости B2: `bce`, `mse` или `l1` |
| `train.iters` | `80000` | число итераций, оно же длина расписания lr |

| `train.weight_decay` | `0.01` | weight decay AdamW |
| `train.warmup` | `1000` | итерации линейного разогрева lr |
| `train.poly_power` | `0.9` | степень poly-спада lr |
| `train.amp` | `false` | bf16 autocast (Ampere и новее): меньше памяти, быстрее |
| `log.every` | `50` | шаг логирования `train/*` |

| `log.val_images` | `3` | число панелей валидации в TensorBoard |

c, t и hr — лучшие значения для SegFormer-B0 на Cityscapes из статьи (табл. XI–XII). Их подбирали для полного попиксельного обучения, так что с патчами и замороженной сетью их, возможно, стоит перебрать. 80k итераций тоже взяты из статьи. Для замороженной сети, скорее всего, хватит 10–20k; проверяйте по кривой `val/mIoU`.

## Перебор гиперпараметров

`src.sweep` запускает случайный поиск по главным гиперпараметрам одной стадии на всех видимых GPU:

```bash
python -m src.sweep configs/sweep.yaml stage=large root=/data/cityscapes   # стадия 1 (B2)
python -m src.sweep configs/sweep.yaml stage=small root=/data/cityscapes   # стадия 3 (B0) с оценкой маршрутизации
```

**Порядок работы:**
1. Перебор `stage=large`. Прогоны ранжируются по `metric`, по умолчанию по `val/hyperbolic_ECE`.
2. Лучшую B2 надо получить в `runs/large`: либо скопировать чекпойнт лучшего прогона (`runs/sweep/large/<номер>/last.pt`), либо обучить заново с напечатанными в конце параметрами (строка `best:`). Затем выполните экспорт (стадия 2) в `runs/large/uncertainty`.
3. Перебор `stage=small`. По умолчанию он берёт `runs/large/best.pt` и `runs/large/uncertainty`. Каждый прогон после обучения проходит через бенчмарк на val в той же точности, что и обучение (`train.amp`). Оценкой служит лучшая mIoU маршрутизации среди порогов, при которых B2 запускается не больше чем на `max_launch_rate` кадров. Предсказание неопределённости B2 училось на этом же val, так что оценка немного оптимистична, а итог проверяется на ACDC.
4. Финальное обучение B0 с лучшими параметрами.

**Что перебирается** (`space` в [configs/sweep.yaml](configs/sweep.yaml)): `model.manifold`, `model.c`, `loss.t`, `loss.hr`, `train.weight_decay`, `train.lr`. Прогон 0 всегда идёт с параметрами по умолчанию, для сравнения. Пространство можно менять. Формат такой:
- `{key: ..., log: [low, high]}` — значение из лог-равномерного распределения;
- `{key: ..., choice: [...]}` — одно из перечисленных значений.

**Батч** подбирается автоматически: максимальный, при котором на каждой GPU остаётся `headroom_gb` свободной памяти.
- **Как подбирается.** В отдельных процессах замеряются шаги обучения и проход валидации на полном разрешении, затем результат проверяется реальным прогоном. Память, уже занятая другими процессами, учитывается по самой загруженной карте: например, если одна из карт выводит рабочий стол.
- **Сколько ждать на 24 ГБ.** В fp32 ориентировочно ~20 кадров на карту для B2 и ~60 для B0. С `overrides=["train.amp=true"]` для B2 примерно вдвое больше.
- **Для всех прогонов один.** Подобранный батч записывается и используется во всех прогонах этого перебора, чтобы их можно было сравнивать.

**Длительность прогона и lr:**
- Число итераций равно `samples / батч`. По умолчанию это столько же кадров, сколько 20k итераций при батче 8.
- Диапазон `train.lr` задан для батча 8 и масштабируется на √(батч / 8). В результатах указан фактический lr, поэтому финальное обучение запускайте с тем же `data.batch_size`, который напечатан рядом.

**Результаты** лежат в `runs/sweep/<стадия>/`:
- `trials.jsonl` — параметры и метрики всех прогонов;
- папки прогонов с `log.txt`, `metrics.jsonl`, чекпойнтами и TensorBoard (`tensorboard --logdir runs/sweep`).

В конце печатается таблица лучших прогонов.

**Повторный запуск** той же команды продолжает перебор: записанные прогоны пропускаются, прерванный продолжается со своего `last.pt`. Чтобы повторить упавший прогон, удалите его строку из `trials.jsonl`. Если меняете `space` или `seed`, задайте новый `out`.

**Размер патча** в перебор не входит, потому что он общий для всего пайплайна. Стадия `small` берёт `model.patch` из чекпойнта B2. Чтобы сравнить размеры патча, проводите обе стадии целиком с `overrides=["model.patch=16"]` и т. п.

**`overrides`.** Несколько значений перечисляются через запятую, каждое в двойных кавычках, а весь аргумент — в одинарных: `'overrides=["train.amp=true","model.patch=16"]'`.

**Время.** На двух картах по 24 ГБ один прогон длится ~30 мин: скорость упирается в загрузку данных, у `small` к этому добавляются ~5 мин на бенчмарк. 20 прогонов на стадию — около 10 ч.

| Ключ `configs/sweep.yaml` | По умолчанию | Что делает |
|---|---|---|
| `stage` | `large` | `large` — стадия 1 (B2), `small` — стадия 3 (B0) с бенчмарком на val |
| `root` | обязательный | корень датасета |
| `out` | `runs/sweep` | папка перебора |
| `trials` | `20` | число прогонов, включая прогон 0 с параметрами по умолчанию |
| `seed` | `0` | сид выборки параметров |
| `samples` | `160000` | обучающих кадров на прогон |
| `validations` | `4` | валидаций на прогон; оценку даёт последняя |
| `gpus` | `null` | число GPU; `null` — все видимые |
| `batch_per_gpu` | `null` | батч на GPU; `null` — подобрать максимальный |
| `headroom_gb` | `2.0` | сколько памяти GPU оставить свободной |
| `workers` | `8` | процессы загрузки данных, всего |
| `overrides` | `[]` | переопределения `train.yaml` для всех прогонов, применяются последними |

| `large_checkpoint`, `large_uncertainty` | `runs/large/best.pt`, `runs/large/uncertainty` | B2 и её экспорт для стадии `small` |

## Время и память

Ниже ориентиры для Cityscapes при батче 8 в fp32. Точность около ±50%, поэтому сначала сделайте пробный запуск.

| Этап | 2× RTX 3080, 80k итераций | 2× RTX 3080, 20k итераций | Память на GPU |
|---|---|---|---|
| 1. B2 | ~2–2.5 ч | ~40 мин | ~5 ГБ, с `train.amp` ~3 ГБ |
| 2. Экспорт | ~5–10 мин | ~5–10 мин | ~4–5 ГБ |
| 3. B0 | ~2–2.5 ч | ~40 мин | ~2 ГБ |
| 4–5. Бенчмарк | ~5 мин на val, ~15 мин на ACDC | то же | ~5 ГБ |
| 6. Отчёт | меньше минуты | то же | без GPU |

На одной RTX 3080 стадия 1 при батче 8 в fp32 занимает ~8–9 ГБ из 10, поэтому включайте `train.amp=true`.

## Частые проблемы

- **`no .../leftImg8bit/<split>/<city>/*_leftImg8bit.png`** (в старой версии кода — `num_samples=0`). `data.root` (в экспорте и бенчмарке `root`) должен указывать на папку, где рядом лежат `leftImg8bit/` и `gtFine/` (см. «Данные»). Если архивы распаковывали через файловый менеджер, он мог создать лишние папки `leftImg8bit_trainvaltest/` и `gtFine_trainvaltest/` — тогда перенесите `leftImg8bit/` и `gtFine/` из них в одну папку.
- **`CUDA out of memory`.** Поставьте `train.amp=true`, обучайте на двух GPU или уменьшите `data.batch_size`; последнее меняет гиперпараметры.
- **`torchrun` зависает на старте.** Запустите с `NCCL_P2P_DISABLE=1`.
- **`data.batch_size=... is not divisible by N GPUs`.** Батч должен делиться на число GPU.
- **`train/img_per_s` не растёт при второй GPU.** Скорость упирается в CPU. Если есть свободные ядра, увеличьте `data.workers`.
- **Нет интернета.** Скачайте веса заранее (см. «Веса»). Если кэш `~/.cache/huggingface` уже заполнен, достаточно `HF_HUB_OFFLINE=1`.
- **T4 или V100.** Оставьте `train.amp=false`: bf16 на них нет.
- **`transformers` 5.x.** Не поддерживается, нужна версия ниже 5.
