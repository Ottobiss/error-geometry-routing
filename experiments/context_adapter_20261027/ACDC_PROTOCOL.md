# Передача E9-k4 коллеге: проверка на ACDC

## Вопрос проверки

Переносятся ли обученные только на Frankfurt состояния B0→B5 на fog/night/rain/snow? Разделить три эффекта: качество роутера, потеря от замороженных настоящих состояний и дополнительная потеря адаптера. Ускорение проверяется отдельно; плотная реализация с масками его не доказывает.

## Что зафиксировать до просмотра результатов

Использовать ACDC validation с разметкой, по всем четырём условиям, с фиксированным списком image-ID. Не обучать и не выбирать эпоху, нормализацию, банк kNN или бюджет на ACDC. Train/ref ACDC для этой проверки не нужны. Не использовать скрытый test для подбора. Сохранить manifest с image-ID, условием, последовательностью, путями, контрольными суммами.

Передать `adapter_best.pt`, `normalization.npz`, `config.json`, `training_complete.json`, `e9k_five_states.py`, `common.py` и этот протокол. Проверить SHA256 по README. Это текущий **MSE-адаптер E9-k4**. E12 пока подготовлен, результата и весов E12 нет.

Для исходного роутера также передать исходный `e8_knn_bank.npy` из Frankfurt и его checksum вместе с конфигурацией извлечения; банк отсутствует в архиве результатов. Если банка нет, провести заранее обозначенный **entropy-only** контроль, не называть его точным воспроизведением rank=entropy+kNN. Не создавать банк на ACDC.

## Подготовка evaluator

Cityscapes-ноутбуки не поддерживают ACDC автоматически: `common.SegSet`, конфигурации и evaluator привязаны к cs_fit/cs_test. Добавить отдельный ACDC dataset/evaluation driver в отдельной ветке, сохранив вычисления адаптера и маскирования. Не запускать train-стадии, не подменять названия доменов в старых результатах.

Изображения привести к 512×1024 тем же resize и RGB-нормализацией, что в `common.py`. Метки ресайзить nearest-neighbor. По поставляемой версии ACDC проверить, что подаётся trainId 0–18, ignore=255; исходные labelId при необходимости преобразовать тем же Cityscapes mapping. Не угадывать кодировку по имени файла. Сохранить policy для invalid/uncertain маски ACDC и применять её одинаково ко всем методам; не смешивать разные политики в одной таблице.

Модели и режим вычислений те же, что в README; eval, веса заморожены. B0 output_hidden_states=True, hidden_states[2] → 160×32×64. Использовать сохранённые x_mean/x_std, затем `Adapter` 160→128→1600 и сохранённые средние/std пяти состояний для денормализации. B5 stage index2 имеет 40 блоков, состояния берутся до блоков 5/15/25/35 и после блока39. Нельзя заменить их выходными feature maps stage3 после layer norm: это другие тензоры.

## Порядок проверки

1. На 1–2 кадрах: обычный B5, B5 с записью состояний и маска «все токены» должны давать одинаковые предсказания с допустимым численным отклонением логитов. Маска «ничего» после слияния обязана дать B0. Проверить размеры и позиции маски; тайл64px=4токена stage3. Показать несколько наложений масок на изображение.
2. На каждом домене получить кэш GT, B0, full B5 и признаки роутера. Один и тот же набор кадров для всех вариантов.
3. Зафиксированные бюджеты тайлов 10/20%; один и тот же выбор тайлов для всех контекстных вариантов. Для точного повторения rank вычислять доменные ранги отдельно fog/night/rain/snow; это трансдуктивный протокол. Не объявлять его онлайн-роутером. Для online-версии нужен отдельно заранее откалиброванный source-порог и отчёт фактического бюджета без подбора на ACDC.
4. Для каждого бюджета и домена оценить варианты из таблицы ниже. Настоящие контексты используют полный B5 как диагностический контроль, не как бесплатный доступный inference.

| Вариант | Контексты | Выход вне выбранных токенов |
|---|---|---|
| b0 | нет | итог B0 |
| b5_full | обычный полный B5 | полный B5 |
| full_tiles | обычный полный B5, слияние только выбранных тайлов | B0 после слияния |
| true_context_true_output | реальные s5/s15/s25/s35 | реальный final |
| pred_context_true_output | адаптер | реальный final |
| true_context_pred_output | реальные | адаптер final |
| pred_context_pred_output | адаптер | адаптер final |
| mean_context_mean_output | сохранённые train-средние | train-средний final |

Stage4 и decoder работают по сформированному полному представлению. Предсказания вне тайлов затем заменяются B0. Не смешивать «вне маски в stage3» и «вне тайлов в итоговой картинке».

## Метрики и сравнения

По каждому условию и суммарно сохранить матрицы ошибок 19×19 **по каждому кадру**, image-ID и sequence-ID. Считать mIoU по сумме матриц, не среднее per-frame mIoU; одинаковая политика отсутствующих классов. Отдельно вывести per-class IoU и согласие с B5 **в выбранных пикселях**, фактическую долю площади, распределение доли по кадрам и corrected/spoiled относительно GT.

Главные сравнения: pred_all против B0, pred_all против true_k4, true_k4 против full_tiles, pred_all против full_tiles. Парный bootstrap по **последовательностям**, не соседним кадрам независимо; 1000 повторов, фиксированный seed, CI в п.п. Для суммарного результата заранее задать pooling по условиям или macro-average условий и сохранить оба явно подписанными. Число независимых последовательностей вывести. Исследовательский статус и множественные сравнения обозначить.

Добавить entropy-only tile routing с обычным B5 и покадровый entropy routing. Для второго: выбирать кадры одним зафиксированным способом, в отчёте различать трансдуктивное ранжирование и источник-порог. Если сравниваются расчётные GOP, дать floor/ceil фактического числа кадров; если полное время — одинаковое железо, dtype, прогрев, синхронизация CUDA, одинаковое включение preprocessing/CPU transfer/роутера/адаптера/слияния. Среднее и p95, память, число кадров и выбранных токенов обязательны.

Плотный masked B5 сейчас считает полные блоки. Замер его времени полезен как цена **текущего кода**, но не демонстрирует sparse acceleration. Сценарий E11 отдельно подписать «не реализован, качество неизвестно».

## Как принять решение

- Если true_k4 близок к full_tiles, а pred_all существенно хуже: ограничение в переносе/согласованности адаптера, не в доказанной невозможности контекстного механизма.
- Если уже true_k4 сильно хуже full_tiles: текущий график заморозки теряет полезный контекст на новом домене.
- Если full_tiles не даёт пользы: сначала оценить роутер и доступный выигрыш B5; адаптер не может гарантировать пользу неудачно выбранных регионов.
- Если pred_all даёт выигрыш к B0: это перенос механизма, но ещё не преимущество над энтропией и не ускорение.
- Новый результат E12 впоследствии проверить отдельной заранее зафиксированной строкой; не выбирать по ACDC лучший checkpoint.

Вернуть `acdc_manifest.json`, конфигурацию/окружение/хеши, CSV по четырём доменам и бюджетам, per-frame NPZ с матрицами и ID, bootstrap.csv, sanity.json, latency.json при наличии и несколько визуализаций. Датасет и тяжёлые активации в git не загружать.
